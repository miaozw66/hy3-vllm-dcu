1、简版和vllm版的残差顺序不同，虽然最终输出在数学等价，但是中间隐藏状态语义不同

2、SDPA attention 维度顺序错误
   问题：F.scaled_dot_product_attention 期望 (B, H, S, D) 格式，但传入了 (B, S, H, D)
   影响：attention 计算在 head 维度而非 token 维度进行，Layer 0 attention_out cos 仅 ~0.80
   解决：在 SDPA 前后 permute 维度：q/k/v permute 为 (heads, seq, head_dim) → unsqueeze(0) → SDPA → squeeze(0) → permute 回 (seq, heads*head_dim)
   修复后：Layer 0 全部 7 个 dump points > 0.9995

3、SDPA 缺少 is_causal=True
   问题：F.scaled_dot_product_attention 未传 is_causal=True
   影响：Layer 0 attention_out cos 从 ~0.90 降到 ~0.80
   解决：加上 is_causal=True

4、vLLM MoE 层在 EP+TP 模式下缺少 TP all-reduce（核心问题）
   问题：DefaultMoERunner._reduce_output 中的 tensor_model_parallel_all_reduce 在 EP 模式下变为 no-op，
        导致 shared expert 和 routed expert 的输出都只有 1/TP 的 partial 结果，未经 all-reduce 就直接相加
   诊断：直接调用 shared_mlp(hidden_states) 的输出与 FusedMoE 返回的 shared_out 完全一致（cos=1.0），
        证明 FusedMoE 没有做 all-reduce
   影响：TP=4 时 MoE 层（Layer 1+）精度极差，05_mlp_out cos 从 0.66 随层数加深降到 0.03
   解决：在 hooked_moe_forward 中手动 dist.all_reduce(shared_out) 和 dist.all_reduce(routed_out)
        注意：dist.all_reduce 默认使用 WORLD group，仅在 TP=EP=WORLD 时正确。
        正确的 group 应该用 get_tensor_model_parallel_group()
   验证：修复后 TP=4 Mean cos_sim 从 0.698 恢复到 0.998（与 TP=1 一致）
   TP=1 时不存在此问题（无 TP sharding，partial=full）

5、MoE 路由 bias 添加顺序错误（sigmoid 之前 vs 之后）
   问题：vLLM 中 router 将 e_score_correction_bias 加在 sigmoid 之后：
        vLLM: topk(sigmoid(logits) + bias), weights = sigmoid(logits).gather(topk_idx)
        MetaInfer: sigmoid(logits + bias) → topk → weights
        这导致专家选择不同（虽仍有 7-8/8 overlap），且路由权重也不同
   影响：MoE 层 05_mlp_out cos 被限制在 0.97-0.98（即使用 BF16 权重替换 INT8 也无法改善）
   解决：在 hooked_moe_forward 中实现 MetaInfer 风格路由：
        router_logits = hidden @ gate_w.T
        scores = sigmoid(router_logits + expert_bias)  # bias 在 sigmoid 之前
        topk_weights, topk_ids = topk(scores, 8)
        topk_weights = renormalize(topk_weights) * routed_scaling
        将自定义 topk_weights/topk_ids 传入 fused_experts()
   验证：修复后 MoE 层 05_mlp_out cos 从 0.97-0.98 提升到 0.999+（大部分层）
        Layer 13 例外：05_mlp_out = 0.982（需要进一步诊断）

6、Shared expert 使用 INT8 量化计算
   问题：shared_mlp() 调用走 INT8 量化线性层（MergedColumnParallelLinear + RowParallelLinear），
        存在 INT8 量化误差
   影响：shared expert 输出有额外损失（远小于路由错误的损失）
   解决：手动对 shared_mlp 的 INT8 权重做 dequantize：
        w_bf16 = (w_int8.float() * w_scale.float()).bfloat16()
        然后用 torch.mm 做 BF16 matmul + SiLU + all-reduce
   注意：shared_mlp 的 gate_up_proj 和 down_proj 权重可能以不同方向存储，
        需要自适应处理：检测 scale dim0 是否匹配 weight dim0，不匹配则 transpose weight
   验证：Mean cos_sim 从 0.994 提升到 0.9988

修复后 TP=4 20层结果（Num layers=20）：
  Mean cos_sim: 0.9988
  Min cos_sim:  0.9819 (Layer 13, 05_mlp_out)
  Points < 0.99: 1/140
  仍然未达到 0.9999 阈值，但已大幅接近

7、Shared expert 的 INT8 vs 手动 BF16 计算对比
   诊断：在 L13, L21, L22 比较 shared_mlp() INT8 输出 vs 手动 BF16 dequantize 计算
   结果：INT8 vs BF16 cos > 0.9996（L13: 0.9998, L21: 0.9997, L22: 0.9996）
   → shared expert 使用 INT8 还是 BF16 对精度影响极小，不是瓶颈

8、fused_experts Triton kernel vs 手动 PyTorch matmul 对比
   诊断：L13 用手动 PyTorch 循环计算每个 expert 的输出 vs fused_experts() kernel
   结果：Manual PyTorch vs fused_experts cos = 0.999988
   → Triton kernel 与纯 PyTorch matmul 结果完全一致，kernel 不是瓶颈

10、Layer 22 深度诊断（2026-08-03，Attempt 2）
   诊断结论：所有组件均验证正确，根因是 INT8 量化误差累积 + MoE 路由放大

   验证通过：
   a) Expert 权重与 checkpoint 完全一致（cos=1.00000000, max_diff=0）
   b) Gate weight 与 checkpoint 完全一致（cos=1.00000072, max_diff=0）
   c) Expert bias 与 checkpoint 几乎一致（cos=0.99999863, max_diff=2.78e-05）
   d) Top-8 路由 ID 完全匹配 MetaInfer（8/8 overlap）
   e) Token 0 的 routing weight 完全一致（renorm+scaled: golden=0.360 vs model=0.360）
   f) Triton kernel 与手动 PyTorch matmul 一致（cos=0.99998868）
   g) BF16 vs F32 精度影响极小（cos=0.99999309）
   h) All-reduce 正常工作（local norm 0.82 → post-AR 2.25）
   i) shared_mlp TP sharding 正确（gate_up_proj: 768/4096, down_proj: 384/4096）

   根因分析：
   - Token 0 的 routing weights 完美匹配（0.360 vs 0.360），但 tokens 1-2 的 MetaInfer
     routing weights 差异较大（golden token1: [0.569, 0.417, ...], token2: [0.670, 0.457, ...]）
   - 这是因为 MetaInfer 使用 BF16 计算 attention QKV/O 投影，而 vLLM 使用 INT8
   - INT8 量化误差在 attention 层累积（Layer 0 attention_out=0.999983 → Layer 22=0.995110）
   - MoE 路由 sigmoid 函数对微小输入差异敏感，将 hidden state 误差放大为 routing weight 差异
   - Token 0（首 token）受影响较小（可能因为 causal attention 使其只依赖自身）
   - Token 1-2（后续 tokens）因 causal attention 依赖前面 tokens 的隐藏状态，误差累积更大
   - 最终 MoE 输出 cos 被限制在 0.962（Layer 22）

   影响层：L13(0.982), L21(0.984), L22(0.962) — 均在 MoE 层出现恶化后又恢复

   可能的修复方向（Attempt 3）：
   - 方案 A：对 attention 层的 QKV/O-proj 权重进行 BF16 解量化计算（替换 INT8 kernel）
   - 方案 B：对 Layer 0 的 dense MLP 也进行 BF16 解量化
   - 方案 C：使用更鲁棒的 routing 策略（如 softmax 替代 sigmoid？但会改变模型行为）

11、Attempt 3：BF16 解量化 attention QKV/O-proj + Layer 0 dense MLP + FP32 RoPE（2026-08-03）

   11a. BF16 attention QKV projection
   问题：manual_attention 中 QKV 投影使用 INT8 ColumnParallelLinear，存在量化误差
   解决：dequant_weight() → torch.mm(h_bf16, qkv_w_bf16.T) 替代原始 INT8 线性层
   影响：attention_out 从 ~0.995 提升到 >0.999（所有层）

   11b. BF16 attention O-projection
   问题：O-proj 使用 INT8 RowParallelLinear，缺少 all-reduce
   解决：dequant_weight() → torch.mm(attn_out, o_w_bf16.T) → dist.all_reduce()

   11c. BF16 Layer 0 dense MLP
   问题：Layer 0 的 HYV3FeedForward 使用 INT8 gate_up_proj + down_proj
   解决：hooked_dense_mlp_forward 中完整 dequantize + BF16 matmul + all-reduce
   验证：Layer 0 全部 7 个 dump points > 0.999997

   11d. FP32 RoPE
   问题：RoPE 可能接收 flat tensor（non-QK-norm 路径），且 BF16 RoPE 精度略低
   解决：确保 q/k 在 head-shaped 下调用 rotary_emb，且使用 FP32 精度
   影响：Mean cos_sim 从 0.999230 提升到 0.999500

12、根因总结（3 次 Attempt 后的最终诊断）

   核心矛盾：
   - INT8 权重解量化 (int8→f32→bf16) 与原始 BF16 权重在数值上可完全一致（max_diff=0）
   - 所有组件验证通过：权重匹配、路由 ID 匹配、Triton kernel 匹配、all-reduce 正确
   - 但 23 层累积的浮点舍入误差（每层 ~1e-4 relative）在 MoE sigmoid 路由处被放大

   误差传播机制：
   1. 每层 attention 和 MLP 的 BF16 计算引入 ~1-2 ULP 舍入误差
   2. 残差连接将误差传递到下一层
   3. MoE 路由 sigmoid 函数对输入高度敏感（导数峰值 0.25）
   4. 微小的隐藏状态差异 (cos ~0.9999) 导致 routing weight 偏差 (cos ~0.968)
   5. Routing weight 偏差直接缩放 expert 输出贡献，放大到 mlp_out (cos ~0.98)
   6. 某些层偶然恢复（后续层路由恰好选择了补偿性 expert 组合）
   7. 退化层位置随计算路径变化，非确定性模式

   无法达到 0.9999 阈值的原因：
   - 方案 A（BF16 attention）: 显著改善但未完全消除（Mean: 0.9982→0.9992）
   - 方案 B（BF16 Layer 0 MLP）: 边际改善（Layer 0 本身已 >0.9999）
   - 方案 C（FP32 RoPE）: 额外改善（Mean: 0.9992→0.9995）
   - 但 sigmoid 路由的本质敏感性意味着即使 1e-4 relative 误差也会被放大 10-100x
   - 要达到 0.9999，需要整个 23 层计算路径（含路由）与 MetaInfer 逐 bit 一致
   - INT8→BF16 解量化无法保证与原始 BF16 权重在所有权重通道上完全一致
     （某些通道的 int8*scale 与原始 f32 的 BF16 舍入可能差 1 ULP）

   可能的终极解决方案（需进一步工作）：
   - 方案 D：使用 MetaInfer 的原始 BF16 权重 checkpoint（非 INT8），完全绕过量化
   - 方案 E：将 INT8 权重替换为原始 BF16 权重后再进行逐 bit 验证
   - 方案 F：对少数退化层（L10/L13/L21）单独诊断其 expert 权重的 INT8 量化损失

     Min cos_sim:   0.978417  ← 受 sigmoid 路由放大影响
