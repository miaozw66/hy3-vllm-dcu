## 第 1 步：设计查证

五代理工作流（run w7cb3ecx2）结论：

- **SupportsPP 接口**（interfaces.py:606-642）：`@runtime_checkable` Protocol，只要求 `make_empty_intermediate_tensors` 属性 + `forward` 签名接受 `intermediate_tensors` kwarg。校验链：`SpeculativeConfig._verify_args`（speculative.py:783）→ `verify_with_parallel_config`（config/model.py:1081）→ `registry.is_pp_supported_model`。
- **参考实现**：NemotronHMTP（nemotron_h_mtp.py:310）、Glm4MoeLiteMTP、GlmOcrMTP 均为 `class X(nn.Module, SupportsPP)` + `__init__` 里挂 `make_empty_intermediate_tensors_factory`。
- **spec config 最小 JSON**：`{"method":"mtp","num_speculative_tokens":1}`（1 个 MTP 层，深度只能 1）。
- **draft 权重加载成本**：MTP 层 = 完整 192 专家 MoE 层，draft 前向不便宜；整体只放末 PP rank（gpu_model_runner.py 注释 NOTE(Jiayi)）。
- **运行时风险**：与三个自研补丁（Gloo PP、_last_replay_stream 同步、tokid 广播跳过）的交互在 -O0 阶段观察。

**输出损坏根因（Patch C，2026-08-13 晚，应"查上游 GitHub 代码"要求逐行对比上游后定位）**：批队列流水线的调度时序缺陷。`step_with_batch_queue`（core.py 419-497）中 call 1 调度 prefill P 后队列未满提前返回，`post_step` 阻塞取出 draft d1 存入 `request.spec_token_ids`；call 2 先调度 B1（此时 `update_from_output(P)` 尚未执行——它在队列满 pop P 时才跑），调度 B1 时请求状态为 `num_tokens == num_computed_tokens == 6`（verified 输出 t1 尚未进入 `_all_token_ids`）而 `spec_token_ids=[d1]`。调度公式 `num_new = num_tokens_with_spec - computed = 1` → B1 是 **spec-only 步骤**：batch 只含 [d1]，放在位置 6 = t1 的位置槽。

worker 侧错位验证：`_calc_spec_decode_metadata`（gpu_model_runner.py 2376-2453）对 scheduled=1/draft=1 算出 `logits_indices = repeat(1-2,2)+[0,1] = [-1,0]`——hidden_states 只有 1 行（d1 自身位置）→ target 与 bonus logits 都取到"看到 d1 之后的 argmax"（预测位置 7），rejection sampler 用它对比 d1：只有重复 token 会被接受（解释 12.5% 接受率与 '北京北京'）；拒绝时 recovered token = d1 之后的 argmax（垃圾，解释 't't'）。同时 KV[6]=d1 而调度器记账认为位置 6=t1，KV/序列发散，每个 spec-only 步骤都产出错位验证的 token → 全序列损坏。输出不稳定是因为多请求并发下时序交错：部分请求调度 B1 时 P 的 update 已跑（正确路径 [t1,d1]），部分没有（损坏路径 [d1]）。正确路径（单 GPU 无批队列）中 post_step 在 update_from_output 之后 → num_tokens=7 > computed=6 → B1=[t1,d1]，draft 与 verified token 同行、用 t1 的 logits 验证——正确。上游 main 的调度公式与 0.18.1 完全一致（/tmp/upstream_scheduler.py 522-531 行），即上游 PP>1 + MTP 同样存在此缺陷（与 #49355 未解决一致）。

**Patch C（scheduler.py schedule()，阻止 spec-only 步骤）**：在 num_new_tokens 计算与 max_model_len cap 之后、`num_new_tokens == 0: continue` 之前插入守卫——同步调度且 `request.spec_token_ids` 非空且 `num_tokens + num_output_placeholders <= num_computed_tokens`（即只有 spec 待处理、无 verified 待处理输出）时 `num_new_tokens = 0` 跳过。跳过路径在 `request.spec_token_ids = []`（line 533）之前 continue，draft 保留；等 `update_from_output` 处理 verified 输出后，下一步 draft 与 verified token 同行（[t, d] 形状）、用正确 logits 验证。不触及 async scheduling（guard 排除）、单 GPU（该状态不可达）、投机 prefill（num_tokens > computed）。每请求最多一个 in-flight 步骤，Patch A 的 claims 机制成为无害的后备。验证：三处 py_compile 通过、内容一致（剥离 CR 后 diff 为空）、补丁标记齐全；独立对抗性验证代理已审查（结论见验证代理报告）。
